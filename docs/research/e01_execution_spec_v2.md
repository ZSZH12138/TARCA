# TARCA E01-v2 解析稳定性验证执行规范

状态：`COMPLETED / PASS / ACTIVE v2`。正式运行于 2026-08-30 完成并已回收到本地。

## 1. 这次实验做什么

E01-v2 不训练 Stage2 模型。它先检查 TARCA 后续实验要使用的“效果测量尺”是否可靠：当答案
可以精确算出时，Monte Carlo 程序能否在重复抽样中给出正确、稳定、足够精确的结果。

E01 分成两部分：

- E01-A 是可精确计算答案的延迟控制环境，用来检查测量程序本身；
- E01-B 是 Lorenz-96，用来确认测量方法在项目正式世界中仍有正确方向。

E01-v1 已经留下完整证据：E01-B 通过，但 E01-A 的五种子端点规则因抽样波动失败。v2 不改写
这个历史，也不重复消耗服务器计算 Lorenz-96；它逐字节核对 v1 最终报告、回收验证、Stage1B
冻结身份和零告警凭据，验证通过后并入 E01-B，只重新运行 E01-A。收尾时，两份 v1 判定证据以
原字节和各自 SHA-256 合并到唯一的 `e01_v1_history_record.json`，其余 v1 执行链已删除。

## 2. 冻结的输入

权威配置是 `configs/e01/e01_v2.yaml`，协议变更记录是
`docs/auth/TARCA_PROTOCOL_CHANGE_CONTROL_CCP_0004.md`。

- 50 个全新 TEST 种子由固定 SHA-256 规则产生，与 v1 的五个种子完全分开；
- 每个种子使用 32、64、128、256、512、1024、2048、4096、8192 个嵌套样本；
- 只运行 `analytic_delayed_control_v1`；
- 同时保留正确 SCM、错误 SCM、错误 lag、随机概念和 identity 五种条件；
- 所有阈值在任何正式 v2 结果产生以前冻结，禁止按结果换种子或改门槛。

旧的“8192 点端误差必须比 32 点端小一半”仍会报告，但只作诊断，不再决定 PASS。原因是两个
随机误差的单次大小并不保证单调，五个种子很容易偶然误拒一个正确程序。

## 3. 通过标准的功能含义

E01-A-v2 必须同时满足：

1. 至少 45/50 个种子的 95% 区间盖住精确答案：测量值没有系统性跑偏；
2. 至少 45/50 个种子的 MCSE 缩小到初始值的四分之一以内：增加样本确实提高稳定性；
3. 至少 45/50 个最终区间的半宽不超过真值的 1%：测量已经足够精确；
4. 50 个最终估计的总体平均偏差不超过真值的 0.5%：大量重复后没有明显偏向；
5. 至少 45/50 个种子在正负一步内找到真实延迟：时间位置能被恢复；
6. 对三种负对照，各至少 45/50 个种子显示正确方法明显更好：程序不是对任何输入都说正确；
7. 至少 45/50 个 identity 条件逐比特为零：什么都没改时，程序不会制造假效果；
8. E01-B 继承凭据必须完整有效：Lorenz-96 的已通过结论没有被偷换。

只有八项全部成立，E01-v2 才 PASS。失败种子必须完整保留，不能静默删除。

## 4. 服务器任务和资源

正式图固定为 101 个任务：50 个 GPU 生成任务、50 个对应的 CPU 分析任务和 1 个最终汇总
任务。GPU 一次只由一个任务占用，避免单卡显存争抢；一个种子的 GPU 数据生成完成后，其 CPU
分析可与下一个种子的 GPU 生成重叠。预检从 8、10、12 条 CPU 分析并发和 2048、4096、8192
三档 GPU batch 中实测选择最快的安全组合，固定保留两个 CPU 核给系统、调度、制品写入和监控。

“吃满硬件”的含义是任务依赖允许时使用全部安全容量，不是强求 CPU/GPU 每秒都显示 100%。
工作量本身较小时，禁止为做高利用率曲线而添加样本或重复正式任务。

预检最长五分钟，OOM、swap、RAM 超过 85%、显存超过 90%、硬件/镜像身份不符、磁盘不足或
预计完成时间侵入一小时回收余量都会停止。预检不使用任何正式种子。

## 5. 可恢复和不可偷看

SQLite 保存 101 个任务、attempt、依赖、心跳和制品引用。制品只有完成原子写入和 SHA-256
校验后才算完成；`resume` 只复用已校验任务，配置、代码、E01-B 凭据、Stage1B 身份或运行
收据漂移时拒绝续跑。

运行结束前，只读前端只显示任务数、进程、资源、预计剩余时间、最近检查点和告警，不显示
任何中间科学指标或 Gate。完整科学结果只能在 101/101 完成后读取。
